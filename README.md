# Data-driven framework for urban air mobility planning in São Paulo

[![Reproducibility checks](https://github.com/Orbolato/UAM-Network-Planning-Sao-Paulo/actions/workflows/reproducibility.yml/badge.svg)](https://github.com/Orbolato/UAM-Network-Planning-Sao-Paulo/actions/workflows/reproducibility.yml)

Code, public/processed data, and reproducibility materials for:

> Carvalho, L.O., Gomes, I.G., Rodrigues, J.F., Murça, M.C.R., Guterres, M.X., Pamplona, D.A. (2026).  
> **Data-driven framework for urban air mobility planning: Integrating socioeconomic and operational factors for optimal network design in São Paulo, Brazil.** *Case Studies on Transport Policy*, 25, 101848.  
> https://doi.org/10.1016/j.cstp.2026.101848

Project page: https://orbolato.github.io/publications/uam-network-planning/

The framework plans an initial Urban Air Mobility (UAM) network for the São Paulo Metropolitan Region (RMSP) in four steps:

1. **Vertiport location** — PAM (k-medoids) clustering of ANAC-registered heliports located in high-income zones of the 2023 Metrô-SP Origin-Destination (OD) Survey. The medoids become candidate vertiports.
2. **Route optimization** — constrained Dijkstra shortest paths between vertiports and SBSP (Congonhas), SBGR (Guarulhos), and SBMT (Campo de Marte) over the Helicopter Special Routes (REH) network. Vertiports and airports cannot be used as intermediate nodes.
3. **Demand estimation** — a daily UAM OD matrix for city-taxi, airport-shuttle, and inter-airport services, built from OD-survey and airport-passenger inputs.
4. **Network expansion** — three additional vertiports (SSUB, SIAV, SIBH) selected using aggregated BIMTRA helicopter-movement evidence, producing a 9-node network when the three airports are included.

## Reproducibility scope

This repository supports several different reproducibility levels; they should not be conflated.

- **Artifact integrity:** [`ARTIFACTS.json`](ARTIFACTS.json) anchors every committed research-data artifact by exact Git blob identity and byte size. CI verifies those anchors.
- **Public preprocessing:** `Rscript run_all.R --preprocess` rebuilds the OD/ANAC-derived processed inputs from the public source snapshots in `data/raw/` before running the analysis.
- **Analysis rerun:** `Rscript run_all.R` runs the analysis from the committed processed inputs.
- **Restricted BIMTRA reconstruction:** the flight-level BIMTRA records are not redistributed. The repository includes the aggregate BIMTRA tables needed by the public analysis, but cannot independently reconstruct them without separately authorized source records.
- **Curated REH inputs:** the archived REH network and complete coordinate reference are analysis inputs, not products of the public preprocessing chain.
- **Paper map screenshots:** several final paper figures were screenshots of interactive Leaflet maps. CI does not claim pixel-identical screenshot regeneration.

See [`PROVENANCE.md`](PROVENANCE.md) for the detailed boundary between source reconstruction, artifact verification, and analysis rerunning, and [`data/README.md`](data/README.md) for file-level data provenance.

## Environment

The public package was tested with **R 4.4.2** and **Python 3.12** on Windows 10.

Install the R packages used by the analysis:

```bash
Rscript install_packages.R
```

Create a Python environment and install the pinned tested package versions:

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

The Python environment is pinned because the package is intended as a research artifact. The original R analysis was not archived with a complete package lockfile; `install_packages.R` therefore records the package set but does not claim byte-identical restoration of the historical R library.

## Quick start

Run from the repository root, or invoke `run_all.R` by path; the orchestrator resolves the repository root from its own location.

```bash
Rscript run_all.R
```

This uses the committed analysis-ready files in `data/processed/`.

To rebuild the public OD/ANAC-derived processed inputs first:

```bash
Rscript run_all.R --preprocess
```

The full preprocessing + analysis run was reported at approximately 20 minutes on the development desktop; runtime depends on platform, package versions, and HTML map rendering.

If the Python interpreter is not discoverable as `python3`/`python`, set it explicitly:

```bash
PYTHON=python3 Rscript run_all.R
```

On Windows, a short clone path (for example `C:\uam`) is recommended. Interactive maps can create deeply nested dependency directories, and older/default Windows path-length settings can fail near the traditional 260-character limit.

### BIMTRA behavior

The flight-level BIMTRA records are intentionally excluded. If an authorized user has them, place them at:

```text
data/raw/bimtra/BIMTRA.csv
```

Then `run_all.R` executes `scripts/05_bimtra_analysis.py`. Without that file, script `05` is skipped and `scripts/06_bimtra_od_map.R` uses the committed aggregate tables under `data/processed/bimtra/`.

### Running scripts individually

The numbered analysis scripts can also be run in order. The route scripts read the vertiports created by the clustering script immediately preceding them:

- run `03` then `04` for the **baseline** network (3 PAM vertiports);
- run `07` then `08` for the **expanded** network (3 PAM + 3 BIMTRA-supported vertiports).

Both scenarios historically write several files with the same names under `output/`. `run_all.R` moves those products to `output/baseline/` and `output/expanded/` after each scenario so they do not overwrite one another.

## Script map

| Script | Role |
|---|---|
| `preprocessing/01_process_od2023.py` | Reads OD 2023 Tables 1 and 6 for zone characteristics/income. It also writes a historical Table-25 interim OD extract that is not used by the final demand pipeline. |
| `preprocessing/02_process_anac_helipads.py` | Filters the ANAC register to heliports in the RMSP municipalities and converts coordinates. |
| `preprocessing/03_extract_od_table30.py` | Converts OD 2023 Table 30 (zone-to-zone daily trips) to long format; this is the OD-demand table used by the network pipeline. |
| `preprocessing/04_prepare_data_en.R` | Translates/standardizes processed column names and writes analysis-ready CSVs. |
| `preprocessing/05_assign_heliports_to_zones.R` | Assigns each RMSP heliport to an OD zone spatially. |
| `01_exploratory_data_analysis.R` | Descriptive statistics, correlations, distributions, and income-based heliport filtering (Section 4.2). |
| `02_helipad_income_threshold_maps.R` | Maps heliports in zones above R$2,500 and R$5,000 per-capita income. |
| `03_vertiport_clustering_baseline.R` | Elbow/silhouette diagnostics for k = 2…8, PAM clustering with k = 3, reclustering, cluster indicators, and baseline UAM OD demand (Sections 3.2, 3.4, 4.3, 4.5). |
| `04_uam_routes_baseline.R` | Builds the REH graph, links vertiports/airports to nearby network points, computes constrained Dijkstra routes, and draws the baseline interactive map (Sections 3.3, 4.4). |
| `05_bimtra_analysis.py` | Filters authorized BIMTRA helicopter movements to RMSP origin-destination activity and creates aggregate heliport/OD statistics (Section 4.6). Requires restricted raw BIMTRA input. |
| `06_bimtra_od_map.R` | Draws the interactive aggregate helicopter OD map from `data/processed/bimtra/`. |
| `07_vertiport_clustering_expanded.R` | Repeats the clustering/demand process while adding SSUB, SIAV, and SIBH as vertiports 4–6 (Section 4.6). |
| `08_uam_routes_expanded.R` | Routes the expanded network; relative to `04`, also considers intermediate REH geometry points, caps connector length, and rejects connectors crossing REH segments. |

Some historical comments and console messages, especially in preprocessing scripts, remain in Portuguese. They are preserved because they are part of the study implementation; public-facing documentation is standardized in English.

## Automated checks

GitHub Actions performs lightweight checks suitable for every push and pull request:

1. compiles all Python source/test files;
2. verifies exact identities and byte sizes for committed data artifacts;
3. validates core CSV schemas and the expected 527-zone / 285-heliport contracts;
4. verifies that restricted raw BIMTRA records are absent;
5. verifies citation/repository metadata and exact Python dependency pins; and
6. parses every R source file with R 4.4.2.

CI deliberately does **not** run the complete geospatial/Leaflet analysis because that would require installing a large system/R dependency stack and would test rendering rather than the public package's structural integrity. The full scientific pipeline remains available through `run_all.R`.
